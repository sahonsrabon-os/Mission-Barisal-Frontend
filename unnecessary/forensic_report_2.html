Section 0 — TL;DR

মূল সত্য: index.php নামে ৬,৪৯০ লাইনের ফাইলটি ভেতরে বিশুদ্ধ HTML+JavaScript — ০টি PHP ব্লক। নামে .php হলেও এটা কোনো সার্ভার-সাইড কোড নয়। এটি শুধু ক্লায়েন্ট। এর সব কল যায় একটাই ঠিকানায়: index.live.php?act=ai…&ai_php_api=<রাউট> — সেই index.live.php-এর আসল সোর্স আপনার কাছে নেই।

তাই এই ডিজাইন: UI-কেই স্পেসিফিকেশন ধরা হচ্ছে (contract-first)। কারণ UI কোডে লেখা আছে প্রতিটি রিকোয়েস্ট কেমন যায় আর প্রতিটি রেসপন্সের কোন ফিল্ড পড়া হয়। আমাদের সার্ভার যদি ঠিক ওই নামের ফিল্ডগুলো ফেরত দেয় — বাড়তি ফিল্ড নয়, হুবহু প্রয়োজনীয় ফিল্ড — তাহলে প্রতিটি ফিচার নিজে থেকেই চলবে।

বিনিময়ে যা অক্ষত থাকে: UI ফাইল byte-identical (md5 895eb75226cc2801834baaced2873bb1), ০ লাইন এডিট, ৩৯টি রাউটের নাম-প্যারামিটার-রেসপন্স অপরিবর্তিত, ১২টি ইভেন্টের নাম অপরিবর্তিত। ফলে কোনো ফিচার ভাঙতে পারে না — কারণ ভাঙতে হলে UI বদলাতে হতো, আর UI বদলাচ্ছে না।

সম্পূর্ণ প্রমাণ: নিচে Section 2-তে ৩৯ রাউটের টেবিল (প্রতিটির প্যারামিটার + যে ফিল্ড UI পড়ে), Section 3-তে ১২ ইভেন্টের পেলোড — সবই সরাসরি index.php-এর লাইন ধরে তোলা।

Section 1 — যুক্তি ১: ফ্রন্টএন্ডই হলো স্পেসিফিকেশন

কেন UI-কে স্পেসিফিকেশন ধরা যায় — ৪টি প্রমাণ

প্রমাণ ১ — পুরো API কল মাত্র ১১ লাইনের একটি ফাংশনে আটকে (লাইন ১১১৬)

function api(a,d,cb){ var iP=!!d, u=A+'&ai_php_api='+a+'&csrf_token='+C, x=new XMLHttpRequest(); x.open(iP?'POST':'GET', u, true); // ডেটা থাকলে POST, নাইলে GET x.setRequestHeader('Accept','application/json'); // সব রেসপন্স = JSON if(iP) x.setRequestHeader('Content-Type','application/x-www-form-urlencoded'); x.onload=function(){ if(x.status===200){ cb(null,JSON.parse(x.responseText)) } else cb('HTTP '+x.status) }; x.onerror=function(){ cb('Network error') }; x.send(iP?bp(d):null); // bp = form-urlencoded বান্ডলার }

এই এক ফাংশনই ৩৫টি রাউটের পুরো রিকোয়েস্ট কনট্রাক্ট। অর্থাৎ:

  • URL প্যাটার্ন একটি: <A>&ai_php_api=<রাউট>&csrf_token=<C>
  • Method নিয়ম একটি: প্যারামিটার আছে → POST (form-urlencoded), নেই → GET
  • Response একটি: সবসময় JSON (HTTP 200), নাহলে UI "HTTP ###" দেখায়
  • বাকি ৪টি রাউট সরাসরি XHR দিয়ে যায় (conversation, file_tree, read_file, resolve_file) + ১টি স্ট্রিম POST (ai_chat_stream) = মোট ৩৯

প্রমাণ ২ — প্রতিটি রেসপন্সের যেসব ফিল্ড UI পড়ে, সেগুলো কোডে সরাসরি লেখা

UI কোডে d.session, d.providers, r.output, d.directories … যেভাবে লেখা, সার্ভারও ঠিক ওই নামে ফিল্ড দিলেই কাজ হয়ে যায়। UI কোনোদিন জানে না সার্ভার ভেতরে PHP না Node — UI শুধু JSON-এর key খোঁজে। এটাই contract-first-এর মূল কথা।

প্রমাণ ৩ — UI-তে ০টি PHP, তাই সার্ভার ভাষা সম্পূর্ণ মুক্ত

grep -c "<?php" → ০। ফাইলের নামে .php থাকলেও ভেতরে কোনো সার্ভার-সাইড লজিক নেই। মানে সার্ভার আমরা যে ভাষায় চাই লিখতে পারি — Node-এর ডিফল্ট মডিউলেই চলবে, PHP লাগবে না।

প্রমাণ ৪ — UI অক্ষত রাখলে drift অসম্ভব

UI ফাইল কখনো না বদলালে (md5 একই থাকলে) কনট্রাক্টও একই থাকে। তাই "আমাদের এডিট করে ফিচার ভেঙে ফেলেছি" — এই ধরনের দুর্ঘটনা বাতিল।

⚠️ এই যুক্তির সীমা (যেন ভুলে না যান)

  • UI শুধু happy path দেখায়: error响应, 403/401, rate-limit — এগুলোর আসল আকৃত UI কোডে পরোক্ষ (যেমন r.error, d.message), তাই সেগুলো প্রমাণ নয়, বলবৎ অনুমান — Section 7-তে প্রতিকার।
  • md5 same ≠ ফিচার correct: md5 প্রমাণ করে UI বদলায়নি, ফিচার ঠিক আছে কিনা তা Section 8-এর রাউট-ম্যাট্রিক্স দিয়ে আলাদা যাচাই লাগবে।
  • বাড়তি ফিল্ড বিপজ্জনক নয়, ঘাটতি ফিল্ড বিপজ্জনক: UI বাড়তি key উপেক্ষা করে; কিন্তু প্রয়োজনীয় key না দিলে ফিচার নিঃশব্দে হাতায়। তাই Section 2-তে প্রয়োজনীয় আর ঐচ্ছিক আলাদা করা।

Section 2 — যুক্তি ২: ৩৯ রাউটের পূর্ণাঙ্গ কনট্রাক্ট

Section 5 — কেন এটা সত্যিই কাজ করবে

৫.১ — কার্যকারিতার যুক্তি (mechanism)

  1. ক্লায়েন্ট-সার্ভার যোগাযোগ শুধু দুই জায়গা দিয়ে: (ক) রিকোয়েস্ট URL+বডি, (খ) রেসপন্স JSON। UI-তে এই দুটোর বাইরে কোনো ডিপেন্ডেন্সি নেই। আমরা এই দুইটিই হুবহু পুনরুৎপাদন করছি।
  2. UI "কী পায়" তা দেখে সিদ্ধান্ত নেয়, "কীভাবে তৈরি হলো" জানে না: JSON.parse(x.responseText) — এর পরে UI শুধু key খোঁজে। Node-এ JSON.stringify বানানো object PHP-র json_encode-এর object-এর সাথে byte-সমান হলেই ফল অভিন্ন।
  3. টুল-এজেন্ট লুপ সার্ভারের দায়িত্ব, UI-এর নয়: UI শুধু দেখে tool-call → tool-result। লুপ চালানো, মডেল কল, টুল এক্সিকিউশন — সব নতুন সার্ভারে। UI কেবল ইভেন্ট খায়। তাই ইভেন্টের নাম-ফিল্ড মিললেই সম্পূর্ণ এজেন্ট আচরণ UI-তে ঠিক দেখাবে।
  4. যা UI পড়ে না, সেটা বাদ দিলেও চলে: আমাদের সার্ভার বাড়তি কিছু না দিলে UI-তে কোনো প্রভাব নেই। অর্থাৎ কনট্রাক্টের ছোট হাত করলেও ফিচার চলে — শুধু বড় হাত করলে চলে না। এটা ঝুঁকির দিক থেকে আমাদের পক্ষে।
  5. এটা ইন্ডাস্ট্রি-প্রতিষ্ঠিত পদ্ধতি: একেই বলে consumer-driven contract testing। বড় বড় কোম্পানি ক্লায়েন্টের প্রত্যাশা ধরে সার্ভার লেখে — আমরা এখানে ক্লায়েন্ট (UI) কাছে প্রত্যাশা শুধু কোড পড়ে বের করছি, অনুমান করছি না।

৫.২ — কেন ভুল হওয়ার সম্ভাবনা কম

  • ফিল্ডের নাম অনুমান নয়, উদ্ধৃত: Section 2-3-এর প্রতিটি ফিল্ড index.php-এর grep থেকে এসেছে।
  • প্যারামিটারের নাম অনুমান নয়: api('fork',{message_id:msgId}) — নাম কোডেই লেখা।
  • Method/Content-Type স্পষ্ট: iP?'POST':'GET' + application/x-www-form-urlencoded — তাই Node-এ URLSearchParams দিয়ে হুবহু পার্স করলেই মেলবে।
  • স্ট্রিম ফরম্যাট স্পষ্ট: line.indexOf('data: ') + JSON.parse(line.substring(6)) — সার্ভার প্রতি ইভেন্টে data: দিয়ে শুরু করে \n দিয়ে শেষ করলেই হবে।
  • CSRF: UI-তে C='' (খালি) — আসল সার্ভার PHP রেন্ডার সময় ভরত। আমাদের সার্ভার index রেন্ডার করলেই C বসাতে পারে, তাই একই নাম ধরে রাখা যায়।

৫.৩ — সৎ কথা: md5 যা প্রমাণ করে, যা করে না

  • ✓ md5 একই থাকলে প্রমাণ: UI অপরিবর্তিত → কনট্রাক্ট অপরিবর্তিত → আগের ফিচার-লিস্ট অক্ষত।
  • ✗ md5 একই থাকলে প্রমাণ হয় না: আমাদের নতুন সার্ভার সব ফিল্ড সত্যিই দিচ্ছে কিনা।
  • সমাধান: তাই Section 8-এ md5-এর পাশাপাশি ৩৯-রাউট ব্যাবহারিক টেস্ট বাধ্যতামূলক — দুইটাই মিলে পূর্ণ প্রমাণ।

  5. পর্যায় ৫ — ওয়ার্কিং-ডিরেক্টরি পরীক্ষা: path/project_id বদলে কল করলে ফাইল-ট্রিই ওই ডিরেক্টরি দেখায় কিনা, ও রুটের বাইরে যায় না কিনা।
  6. পর্যায় ৬ — প্রোভাইডার সুইচ: দুইটি আলাদা base_url বসিয়ে test_connection + স্ট্রিম দুটোই চলে কিনা।
